# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a Python-based PDF parser and converter that transforms legal PDF documents (acts, SEBI circulars, eGazette notifications, amendments) into structured HTML/manifest output. The tool extracts text content, detects document layout (headers, footers, sections, paragraphs, tables, figures), and applies document-type-specific processing rules.

## Core Architecture

### Main Components

- **Main.py** (`source/Main.py`): Primary orchestrator (`Main` class) that coordinates the entire parsing workflow
  - Converts PDF to XML via `ParserTool` (pdfminer-based) or `ChromeLensParserTool` (for scanned copies)
  - Dispatches processing to type-specific pipelines: `acts`, `sebi`, `sebi_circulars`, `egazette`, or default
  - Manages the page processing pipeline through `Page` objects
  - Builds final HTML output using `HTMLBuilder` / `HTMLBuilderChromeLens`
  - Implements header/footer detection across all pages using sequence matching
  - Writes an IIIF manifest (`Manifest.py`) for `egazette` and `sebi` type documents

- **ParserTool.py** (`source/ParserTool.py`): PDF processing interface
  - `ParserTool`: uses pdfminer's `pdf2txt.py` to convert PDFs to XML format and parses XML to extract page elements
  - `parse_xml()`: the single place the pdfminer XML is parsed. pdfminer writes each glyph's decoded character straight through, so a font whose `ToUnicode` map has a hole (the glyph maps to U+0000) puts a raw NUL in the XML - which XML 1.0 forbids as character data, making `ET.parse` reject the whole file and the document fail outright (3234 of them in a 31-page Mangal gazette; see the `ToUnicode` repair below, which fixes the *cause*). `parse_xml` tries a plain parse first, so a well-formed file pays nothing, and only on `ParseError` re-reads the file and strips the characters XML 1.0 forbids; a `ParseError` that stripping does not account for is re-raised untouched rather than swallowed, and the cleaned text is re-encoded to bytes so the file's own `encoding="utf-8"` declaration still holds. A `<text>` element emptied this way keeps its bbox and simply contributes no text, which every consumer already handles (`t.text and t.text.strip()`, `child.text or ''`, `get_text(char) or ''`)
  - `ChromeLensParserTool`: OCR-based extraction path (chrome-lens / OCR) used for scanned copies

- **Page.py** (`source/Page.py`): Individual page analysis and classification
  - Processes textboxes and determines page layout (single/multi-column)
  - Classifies content into: headers, footers, sections, paragraphs, side notes, tables, figures
  - Uses ML clustering (DBSCAN, KMeans) for layout analysis
  - `detect_multicolumn_layout()`: detects genuine 2-column page layouts via KMeans on textbox x-centers, gated by column item-count/height-coverage/gap/overlap checks; the gutter-width check is font-size-relative (em-based) rather than a fixed fraction of page width, so it generalizes across documents with different physical page widths and font sizes; candidates that are centered/full-width (titles, running headers) or that look like rotated/vertical text (e.g. chart axis labels, filtered via a height>width aspect-ratio check) are excluded from the clustering input so they don't produce false positives
  - `apply_column_reading_order()` / `_reorder_by_columns()`: once a page is flagged multi-column, rebuilds `self.all_tbs` into band-based reading order — all of the left column top-to-bottom, then all of the right column top-to-bottom, treating only genuinely full-width items (headings that span both columns) as band separators — so downstream hierarchy/section detection and HTML building consume the correct linear order
  - Detects borderless tables via `TableExtraction` when `-te/--table-extract` is set

- **HTMLBuilder.py** (`source/HTMLBuilder.py`): HTML generation with structured output
  - Converts classified content into semantic HTML
  - Applies CSS styling for different content types (sections, paragraphs, amendments)
  - Maintains document hierarchy
  - Column-aware: reads `page.column_bounds`/`page.is_multicolumn` to keep sentence-completion detection (`SentenceEndDetector`) column-relative instead of page-width-relative, so a sentence continuing from the bottom of the left column to the top of the right column isn't mistaken for two complete sentences
  - **Font names in the output (`-fn/--font-names`)**: every contiguous run of text drawn in one pdf font is wrapped in `<span data-font="FONT">...</span>`. The font is *not* carried through the builder as markup - the builder reads the text it is given to decide what to emit (a section's number, a paragraph's last token, the punctuation a sentence ends on), so a tag in the middle of it would change the document's **structure** rather than just annotate the result. It is carried as a mark in the text instead (`TextBox.FONT_MARK_START`/`FONT_MARK_END`, two private-use characters nothing a pdf draws can be mistaken for), and `HTMLBuilder.render_font_spans()` turns those marks into real spans once, on the finished html. Everything in `HTMLBuilder` that *reads* the text goes through `plain()` (`strip_font_marks`) and everything that emits it keeps the marks; where a regexp has to run on the plain text and its halves are then emitted (`addSection`'s section number), `split_marked_text()` cuts the marked text at the plain text's own index and hands the tail the font that was in force. A mark always sits immediately before a non-space character - whitespace, and the footnote placeholder the tool inserts itself, carry no font of their own and simply continue the run around them - which is what makes the `str.strip()` calls all over the builder unable to separate a run of text from the mark naming its font. A span never crosses a tag (so the html stays well nested and no font leaks past the text it belongs to) and runs of the same font that meet inside one stretch of text - the end of one textbox and the start of the next - are merged into a single span. **A font the detector was run on carries a second attribute naming what the model made of it** (`<span data-font="TT572t00" data-detected-font="krutidev">`): `Main.detect_unknown_fonts` records every verdict in `Main.detected_font_classes` (it runs before `set_htmlbuilder()`, so the map is complete by the time a builder is made) and `get_htmlBuilder` hands that map to `HTMLBuilder`, where `font_span()` looks the font up by the same name the mark carries - the `font` attribute of the pdf's own `<text>` elements, which is what both sides are keyed by. The attribute reports the model's answer **as it stood, not the decoder that was run**: a verdict too unsure to act on, or impossible for the script of the text it was reached on, is rejected by `get_detected_font_key()` and still reported here, since a rejected verdict is precisely what someone reading the output to see how detection went needs to see (the label is also the model's class, so a `nirmala` verdict says `nirmala` where the converter it points at is `nirmalaui`). A font detection never ran on carries `data-font` alone - one placed by its name, by `-fc` or by the `ToUnicode` repair, one drawing fewer than `FONT_DETECT_MIN_WORDS`, one whitelisted out by `FONT_DETECT_SKIP_RE`, and every font at all under `-nfd`. The flag is html-only: `acts`/`sebi_circulars` are written as bluebell and it is refused for them with a warning (`BLUEBELL_PDF_TYPES` in `Main.py`), and `judgments` (`JudgmentBuilder`, a class of its own rather than a subclass of `HTMLBuilder`) and the OCR path don't carry it either. Table cells are not annotated: they are assembled by camelot/`TableExtraction` from a dataframe rather than from a textbox's own text. Covered end to end by `lsdebate.pdf` in `test/test_cases.csv`, whose baseline with every `<span data-font>` stripped back out is byte-identical to what the tool produced before the option existed
  - `HTMLBuilderChromeLens` handles the OCR/scanned-copy output path, with its own independent word-level column-gutter detection (`_detect_word_columns`) based on the fraction of rows with ink in each x-bin, and row splitting/reordering (`_split_row_by_column`, `_reorder_rows_by_column`) into left-then-right reading order

- **Acts.py** / **SebiCirculars.py**: Document-type-specific builders (`Acts`, `SebiCirculars`) mixing in `TableBuilder` (`Table.py`) and `SentenceMaker` (`SentenceEndDetector.py`) for type-specific section/sentence handling

- **Amendment.py**: Detects and structures amendment content within legal documents

- **TableExtraction.py**: Table detection/extraction, including borderless-table detection using `camelot-py` (bordered/lattice tables) and lightweight logistic-regression classifiers (`PenalizedLogisticClassifier`, `HeaderRowClassifier`, `RegionMergeClassifier`, `ContinuationClassifier`) for header-row, region-merge and cross-page-continuation decisions on borderless tables. These classifiers are trained online via reinforcement learning (`PenalizedLogisticClassifier.reinforce()`, a REINFORCE-style policy-gradient update) — the reward for each decision is derived from the eventual downstream quality of the region it helped build (`fill_ratio` if accepted as a table, a shortfall-based penalty if rejected), not from the classifier's own prediction confidence. Classifiers start from fixed default weights every run and are shared across a document's pages only for the duration of that run — nothing is persisted to disk, so results are reproducible run-to-run and one document can't bias another's classifier state
  - **Cross-page table continuation**: a borderless table can run off the bottom of one page and resume at the top of the next (e.g. a multi-page amendment schedule with `Sl.No | Year | No. | Short title | Amendments` columns spanning dozens of pages). After building a page's tables, `BorderlessTableExtraction._compute_continuation_out()` decides whether a table is likely to continue and, if so, emits a `continuation_out` column template (per-column x-ranges normalized by page width, plus row-count/header hints). The trigger is any of: the table covers ≥30% of the page area (`continuation_page_coverage`); its bottom edge sits in the page's bottom margin (`continuation_bottom_margin_ratio`); or it contains a **column-ruler row** — a row of short parenthesised ordinals like `(1)(2)(3)(4)(5)` or `(i)(ii)…` (`_table_has_column_ruler`), the caption row a formal schedule repeats on every page — which seeds the chain from a table's columns even when that first fragment was detected small (e.g. its long trailing cell truncated, or its bottom paragraph mis-labelled as a footer). `Main` threads the template forward (`self.pending_continuation`) into the next page's `get_borderless_table`.
    - When a template is active, `get_table_and_bbox` runs `_detect_continuation_table()` **first**, over all candidate items, so it gets first claim on the top-of-page region before normal per-page detection (which is prone to mis-splitting a wide free-text column into fake columns via its lettered `(a)/(b)/(A)` sub-items) can carve it up; normal detection then runs only on the leftover items, and any normal table overlapping the continuation (`_suppress_normal_tables_within`) or falling inside the template's x-span on a single-column overflow page (`_suppress_normal_tables_in_span`) is dropped as a mis-split of the same text.
    - The continuation runs *independently of* normal detection (which needs a full multi-column structure and a header): it clusters the items into rows by top-edge (`_rows_by_top`, a fixed line-height epsilon rather than the general auto-eps clustering, which fuses regular rows) and walks rows from the top. Row inclusion is **band-based, not tied to matching a specific column**: a row is taken if the majority of its items fall within the template's horizontal band, and *every* item in an included row is kept (not just the in-band subset) - a cell that overruns its column slightly must not vanish just because the row around it qualified for inclusion. Column matching/tracking is handled by `ColumnTracker` (below). The walk is alignment-agnostic to vertical gaps — because the template is trusted, large gaps are paragraph breaks inside a wide column, not table ends — and stops only on a run of out-of-band rows (`continuation_max_skip_rows`) or a section-sized gap. A continuation may legitimately drop its header row and carry only *some* columns, so acceptance is decided by `ContinuationClassifier` on purely coordinate-alignment features (strict column coverage, x-span overlap, closeness to the page top, row support vs the previous page's row count, and mean column-edge *overrun*), gated to abut the page top (`continuation_top_band_ratio`), expose ≥`min_cols` strictly-matched columns, and clear a deliberately low fill bar (`continuation_min_fill_ratio`).
    - **`ColumnTracker`**: column positions are never a single frozen snapshot. Each column keeps a running (count-weighted) average of the x0/x1 of every item assigned to it (`ColumnTracker.update`), so genuine drift across a long chain is absorbed instead of causing later rows to fail alignment and lose their text; its tolerance band only ever widens to the largest cell actually seen, never shrinks. Items that are in-band but don't strictly match any tracked column ("orphans") are collected across the whole walk and, if several recur at the same x, promoted into a brand-new column (`ColumnTracker.add_column`, `_promote_orphan_columns`) - but only when that x-range is disjoint from every already-tracked column, so lettered sub-clause markers ("(A)"/"(a)") recurring inside one wide free-text cell are never mistaken for a second column nested inside the first (that misfire previously corrupted the propagated template down the chain). Any item that still matches nothing (a genuine stray) falls back to its nearest tracked column by centre distance with no tolerance gate - nothing reaching this point is ever left unassigned. `_recover_unassigned_items` (normal per-page detection) uses the same tracker, run as an iterative flood-fill: each newly recovered item both grows the row-span search window and nudges its column's running average, so genuine cells sitting just outside the initial window (e.g. a long free-text cell's trailing paragraph) are no longer silently dropped.
    - **Labelling by source box, not bbox**: every accepted table (normal or continuation) records the exact set of source textboxes its dataframe was built from (`table_item_objs`), and `Page.label_borderless_table_tbs` marks precisely those boxes as `("borderless_table", idx)` rather than any box whose coordinates fall in the table's bounding box. This guarantees the dataframe is a superset of everything labelled (no text is labelled-as-table but dropped from the output) and stops a wide table's y-only bbox test from sweeping in neighbouring prose (fewer pseudo-detections).
    - **Header/footer/side-note reclaim**: adaptive header/footer/side-note detection runs page-wide, before any table detection, purely on cross-page text similarity - it has no notion of "this box is a table cell". A short, frequently-recurring cell (e.g. "Penalty which may extend to X lakh rupees.", varying only in the number, or a column caption like "Year No." that happens to sit where a side-note would) can be mistaken for boilerplate and stripped before border-table code ever sees it. Two complementary reclaim passes run in `Page.get_borderless_table`: (1) `reclaim_header_footer_for_continuation`, gated on an *incoming* continuation template, reclaims anything in the page's top band and horizontally within the inherited column span (even a single-column template) - this is the only pass that can fire before any detection has run on this page, so it's what makes a continuation's very first row recoverable; (2) `reclaim_header_footer_within_bbox`, gated on nothing but general - it runs a cheap **probe pass** (`BorderlessTableExtraction(..., rl_enabled=False)`, so it can never pollute the shared RL classifiers even though its result is discarded) purely to see this page's own preliminary table bbox(es), reclaims any header/footer/side-note box whose centre actually falls inside one (top or bottom edge, any page including a table's *seed* page), and only then runs the real, RL-enabled detection pass that becomes `self.borderless_tabular_datas`. Together these two passes mean a mislabelled header/footer/side-note box "counts" as still-under-the-table content regardless of whether the page has an incoming template or not.
    - **Spine-column selection is corroboration-aware but not corroboration-blind**: `_select_spine_column` (used by `_form_regions` to anchor row-banding for a table with wildly uneven cell heights) can be fooled when reclaim adds a header/footer box back as a candidate: two identifier columns that only populate *once per logical entry* (not once per row - e.g. "Sl.No."/"Year" on a schedule page with a single new entry) can end up with the same small item count and matching y-positions, "corroborating" each other into looking like the true row-count anchor, collapsing what should be ~15 row-bands into 3 (with everything else crushed into one oversized cell). The fix: after finding a corroborated pair, a much larger and still reasonably clean column (`count ≥ 2× the corroborated count`, e.g. the table's dominant free-text column, populated on every row) takes precedence as spine instead - the sparse identifier columns are still correctly folded into its row-bands afterward by the normal overlap-based assignment, just not used to *define* the bands.
    - **Lopsided ("spine") tables**: a table with one dominant free-text column (present on almost every row, e.g. a schedule's "Amendments" column) and sparse identifier columns (populating only once per logical entry) has a legitimately low average cell-fill ratio and low multi-column-row ratio purely from that shape, not from being a bad table. `_has_spine_column` (a column present in ≥80% of rows) is checked consistently at every acceptance gate that would otherwise reject this shape: `_prune_weak_columns` uses a flat row-support floor instead of one scaled to total row count once a spine exists; `_passes_multi_col_row_check` accepts if a spine is present and at least `min_narrow_col_support` rows demonstrably combine it with another column; and the final accept gate in `_detect_page_tables` uses `min_fill_ratio_with_spine` (much lower than `min_fill_ratio`) instead of the flat ratio. `_trim_non_tabular_edge_rows` (which strips genuine stray intro/closing prose directly abutting a table) is similarly scoped: a single-column edge row is only stray if it's *wide* relative to the table's overall width (≥75%), not merely single-column - and stripping is capped to at most 2 rows per edge - since single-column-ness alone is the normal, legitimate shape of most rows in a spine table and previously caused unbounded runs of genuine trailing rows to be discarded as if they were incidental prose.
    - **Template propagation is a union, never a replace**: when the page whose table is being handed forward is itself a continuation, its own column detection for that page might only be a subset or a momentarily noisy split. `_continuation_out_from_tables` merges this page's own column ranges with the inherited template's by x-range (`_merge_column_ranges`, treating overlapping/adjacent ranges as the same physical column) rather than picking one set by raw column count - so an established column that a later page's detection stumbles on can never be permanently dropped; the chain can only keep learning the full structure, not lose it. Column ranges fed into this merge are read from `ColumnTracker`'s own running-average bounds, not the raw min/max of every item ever assigned to a column, so a single stray item placed via the nearest-column fallback can't stretch a column's reported territory and corrupt what gets propagated.
    - **Passthrough**: a page that is a *single-column* overflow of the inherited table (e.g. a whole page of the `Amendments` column continuing) emits no table of its own but still propagates the template forward (`continuation_passthrough`), so the chain survives runs of single-column pages and reconnects when a later page resumes the full multi-column structure. The chain stops only when a page's content neither triggers nor passes through

- **Figure.py**: Image/figure extraction and writing (`Pictures`, `StableImageWriter`)
  - **PNG-predictor stride fix** (`apply_png_predictor`, `patch_png_predictor`, installed over `pdfminer.pdftypes.apply_png_predictor` at import): pdfminer computes a predicted stream's scanline stride with a floor division (`colors * columns * bitspercomponent // 8`) where the PNG spec rounds up, so a sub-byte image whose width isn't a multiple of 8 loses the last, partial byte of every row and, from the second scanline on, reads a byte of pixel data where the row's filter type should be. That is a **1-bit image mask** - how a court seal, signature or letterhead in a judgment or gazette is stored - and it fails one of two ways depending on what the stray byte happens to hold: a value above 4 raises (`PDFValueError: Unsupported predictor value: 255`, or `IndexError: list index out of range` from a filter looking back into a short row) and `get_images` logs the image and drops it entirely (`test/test_judgment_pdfs/judgment27.pdf` at 194px, `judgment4.pdf` at 135px and `judgment51.pdf`/`judgment63.pdf`/`judgment88.pdf` at 310px all lost their seal that way - restoring it is the only change in those five baselines); a value of 0-4 is taken for a real filter type and the image is written out silently sheared instead (`judgment14.pdf` at 100px, `judgment66.pdf` at 147px, `judgment5.pdf` at 123px - the html records only the image's name and size, so a corrupt one moves no baseline and nothing reports it). The replacement differs from pdfminer's only in rounding both the stride and `bpp` up (and never letting `bpp` fall below 1, so Sub/Average/Paeth still look a whole pixel back); it is byte-identical to pdfminer's on the 8-bit data pdfminer already handles, bar one further case pdfminer gets silently wrong - it seeds `line_above` with `columns` zero bytes instead of `colors * columns`, so an **RGB** image whose *first* scanline uses Up/Average/Paeth is truncated to a third of that row with no error at all. `patch_png_predictor()` probes the installed pdfminer with four rows of a 13px 1-bit image and only patches if that comes back wrong, so a pdfminer that ever fixes this keeps its own (very likely faster) implementation. `pdftypes` binds the name at import, which is why that module - not just `pdfminer.utils` - is the one patched. Nothing else in the pipeline is affected: `ParserTool` runs pdfminer as the `pdf2txt.py` subprocess and extracts no images, so this decoder is reached only through `Figure.get_images`

- **Manifest.py**: Builds IIIF **Presentation API 3.0** manifests (`IIIFManifest`, via the `iiif_prezi3` library - `Manifest`/`Canvas`/`AnnotationPage`/`Annotation`/`AnnotationBody`, not the older 2.1 `sequences`/`canvases`/`images` shape) for `egazette` and `sebi` image-based documents. Every resource identifier in the manifest - manifest `id`, canvas `id`s, annotation page `id`s, annotation `id`s, the image body's `id`, thumbnail `id`s, Image API service `id`s - is built through exactly two choke points: `_manifest_uri(*parts)` (joins onto `self.manifest_base_uri`) and `build_uri(resource_path, sub_dir="images")` (same anchor, for files written under `manifest_dir/<sub_dir>/...`; `sub_dir` defaults to `"images"` but isn't hardcoded to it, so a future file-backed resource type gets identical treatment for free by passing its own `sub_dir`, without a new mechanism). `iiif_prezi3`'s helpers (`make_canvas`, `add_image`, `add_thumbnail`) take explicit `id=`/`anno_id=`/`anno_page_id=` args rather than generating URIs themselves, so there's no library auto-naming to fight - full manual control over every ID, same principle the old 2.1 code already used.
  - **IIIF Image API 3.0 Level 0 service** (`_write_level0_image_service`): these are plain pre-rendered static files, not served by a real dynamic image server, so a Level 1/2 service (arbitrary region/size/rotation) would be a lie - Level 0 compliance is what actually fits: a client only ever needs `info.json` (capabilities) and the single canonical `{id}/full/max/0/default.{format}` request to both genuinely resolve. Both are physically written (`manifest/<label>/images/<page_id>/info.json` and `.../full/max/0/default.<ext>`, a real file copy) rather than just referenced - a viewer speaking the Image API protocol gets a working response, not a 404. Each canvas's painted image body's `id` is this canonical service URL (not the flat `images/<file>` URL), with the `ImageService3`/`level0` service attached to the body pointing back at the same `info.json`; the flat `images/<file>` file also still exists unchanged (Figure.py writes it there for inline HTML embedding, independent of the manifest) so a static file *is* duplicated on disk by this - the real cost of Level 0 actually functioning rather than just being declared. Thumbnails stay pointed at the flat file (no dynamic resizing capability to route them through the service for).
  - **`rights`/`provider`/`requiredStatement` (attribution)**: purely optional, additive, and **never fabricated** - this codebase has no license/organization/attribution configuration anywhere (checked; `README.md` explicitly states no license file exists), so these fields are emitted *only* when a caller supplies real values via `-rt/--rights`, `-pi/--provider-id` + `-pn/--provider-name` (both required together - IIIF's `Provider.id` is a required URI, a name-only or id-only provider is either invalid or useless, so a partial pair is dropped with a logged warning rather than emitted broken), and `-at/--attribution`. `rights`/`provider_id` are validated to look like URIs (`Main.is_url_like`, used here as a *positive* check - unlike `output_dir`/`server_root` where the same helper guards against a URL being supplied by mistake) and dropped with a warning rather than failing the whole run if malformed, since these are decorative metadata, not structural.
  - **No local filesystem paths in the manifest's `metadata`**: `Main.write_manifest()`'s `"Generated from"` metadata entry uses `Path(self.pdf_path).name` (filename only) rather than `self.pdf_path` itself - the manifest is a *publicly served* file, and embedding the raw input path (however it was supplied to `-i`, absolute or relative) would leak local server details (username, directory layout, project/repo structure) into it. The `label` field was already safe (`Path(self.pdf_path).stem`, which also drops the directory) - this was the one remaining place a path could leak.
  - **What becomes a canvas**: one canvas per entry in `self.unique_images` (the same deduplicated pool of embedded raster images `Figure.py` collects for inline HTML images) - **not** one canvas per PDF page. This is intentional, not a limitation to work around: for a text-layer eGazette most pages have no embedded image at all, so "one canvas per page" isn't meaningful here: the manifest is a gallery of the images the document actually contains (stamps, letterheads, scanned inserts, photos), each traceable back to its real source page.
  - **Canvas labels reflect real source pages, not a sequential counter**: `Figure.register_global()` already tracks every page number a (deduplicated) image was seen on (`unique_images[hash]["pages"]`, a set of page-id strings from the source XML). `Main.write_manifest()` sorts images into that page order (`page_sort_key` - numeric-aware, since page ids are strings like `"1"`/`"12"` and a naive lexicographic sort would put page 12 before page 2) and carries `pages` through to `Manifest.generate_iiif()`, which labels each canvas `"Page {n}"` (or `"Pages {n1}, {n2}"` if the same image recurred across several pages pre-dedup) instead of a meaningless `"Canvas 1"`/`"Canvas 2"`.
  - **OCR text is surfaced, not discarded**: `Figure.extract_text_content()` already runs a real OCR pass on every candidate image purely to decide whether to *keep* it (an image with no detectable text is dropped) - the extracted text and detected language (`Figure.detect_language`) were being computed and then thrown away. They're now threaded through (`extract_text_content` returns `(text, language)`; `register_global`/`unique_images` carry both) and, when present, attached to the canvas as an inline IIIF "supplementing" annotation (`TextualBody`, `motivation: "supplementing"`, `format: "text/plain"`, real detected `language`) - no new resource file, no extra HTTP fetch, just embedded directly in `manifest.json`. An image whose OCR pass failed (or that had no page association) still gets a fallback `"Image {n}"` label and simply has no `annotations` property - never an error.
  - **`-sr/--server-root`** (`Main.server_root` → `IIIFManifest(..., server_root=...)`): a *local filesystem* directory representing the web server's document root - e.g. `server_root=/var/www`, `output_dir=/var/www/gzdl/html/andhra/2025-01-02` → every manifest URL gets `gzdl/html/andhra/2025-01-02` inserted between the public base URL and `manifest/<label>/...` (`IIIFManifest._resolve_url_path_prefix`, feeding into `self.manifest_base_uri`, the single upstream anchor for both `_manifest_uri`/`build_uri`). Never given (or `output_dir == server_root`): identical to the pre-`-sr` behavior, no extra segment - full backward compatibility. `output_dir` not located inside `server_root` is a **validated, fail-fast error** (`ValueError`, both paths named in the message) - checked in `IIIFManifest.__init__` and, redundantly for speed, in `Main.__init__` itself (before anything, including `DynamicFontMapper`, touches the filesystem - same placement as the `is_url_like` check below) so a misconfigured `-sr` is caught before any document processing, not after. `server_root` is - like `output_dir`, and unlike `-pu` - purely a filesystem input: it is never written to, and `Main.is_url_like()` guards it the same way `output_dir` is guarded (catches `-sr`/`-pu` being swapped).
  - The public base URL used for every URI in the manifest is independent of the local output directory and must be supplied via `-pu/--public-base-url` (or the `PUBLIC_BASE_URL` env var) since there's no mechanical way to derive a public serving URL from a local filesystem path - `output_dir` (and now `server_root`) are used *only* to know where files live/get written and how to express that as a URL *path*, never as a source for the URL's scheme+host. `Main.write_manifest()` warns loudly (not just silently) when neither `-pu` nor `PUBLIC_BASE_URL` is set, since it then falls back to `http://localhost:8000`, which is almost certainly wrong outside local development. `Main.is_url_like()` guards the other direction for both `output_dir` and `server_root`: validated (in `Main.__init__`, before anything - including `DynamicFontMapper` - touches the filesystem; redundantly again in `parsePDF()` and `write_manifest()` for `output_dir`) to make sure neither was ever accidentally given a URL itself (e.g. `-o`/`-pu`/`-sr` swapped) - `Path(url).resolve()`/`os.makedirs(url)` don't error on a URL string, they silently mangle it into a bogus nested local directory (e.g. `https://host/a/b` → `<cwd>/https:/host/a/b`) and happily write files there, so this is caught with a clear `ValueError`/logged error instead of silently doing the wrong thing.
  - `Main.write_manifest()` (called from `parsePDF()` when `pdf_type in {'egazette', 'sebi'}`) skips manifest generation entirely (and `Main.remove_empty_manifest_dir()` cleans up the resulting empty `manifest/{pdfname}/` folder) when a PDF has no extractable images, since an IIIF manifest with zero canvases isn't meaningful. When a manifest *is* created, `write_manifest()` records its public URI (`IIIFManifest.get_manifest_uri()`) in `Main.manifest_url`; `Main.write_html()` (via `add_manifest_link_to_html()`) then injects a `<p><a href="...">click here for iiif manifest</a></p>` link right after `<body>` in the HTML output for those two types - `write_manifest()` always runs before `buildHTML()` in the normal flow (`parsePDF()`, then the caller runs `buildHTML()`), so the URL is available by the time the HTML is written; no link is added when `pdf_type` isn't one of `{'egazette', 'sebi'}` or no manifest was produced

- **CompareLevel.py**: Heading/section level comparison logic (`CompareLevel`, `CompareLevelSebi`)

- **FontMapper.py**: Dynamic font mapping (`DynamicFontMapper`) used during text normalization

- **FontSurvey.py**: Standalone utility (not part of the parsing pipeline) that inventories the fonts used across a set of PDFs. `FontSurvey.survey()` takes any mix of directories, single PDFs and wildcard patterns (`-i` is `nargs='+'`), and per PDF page merges two sources: `page.get_fonts(full=True)` for every font *declared* in the page resources (type, format, embedded-or-not, encoding, and whether the font object has a `ToUnicode` entry) and `page.get_text("dict")` spans for the text actually *drawn*, attributed to the span's font. Fonts are identified by base name with the per-file 6-letter subset prefix (`ABCDEF+`) stripped, so the same font subset differently in different files counts once; the raw subset names are kept as a detail. Each font keeps up to `-mw` (default 100) distinct words in first-seen order plus a total word count. Fonts are ranked by the number of documents they are *genuinely drawn* in (`drawn_files`), not the number that merely declare them - a page's resources routinely list fonts no text ever uses, and those would otherwise inflate a font's apparent reach; declared-only documents are still recorded (`files`, and a `[+N declared only]` note in the report), and a font never drawn anywhere is still listed rather than silently dropped. **A font's file list is ordered by the share of each document's words that font draws** (`FontRecord.get_file_shares`, this font's words in that file over every word drawn in it by any font - `FontSurvey.get_file_totals()`), biggest share first, with the share printed beside each filename (`<1%` rather than a misleading `0%` for a font drawing a handful of words in a huge document) and carried in the JSON as `drawn_file_shares`. Ranking by share rather than by this font's own word count is what makes the list answer "which pdf should I open to look at this font" - a font that sets an entire short document outranks one drawing a few headings in a long one; a declared-but-never-drawn font has no share and falls back to a name-sorted list. A font that is drawn but whose every token is punctuation or a symbol glyph (bullet fonts like `Symbol`, rule characters) is labelled as such instead of being reported as undrawn.
  - **Wildcards work whether or not the shell expands them**: an unquoted `-i pdfs/*.pdf` arrives already expanded into many arguments (hence `nargs='+'`), while a quoted `-i "pdfs/**/*.pdf"` arrives as one literal pattern and is expanded by `get_pdf_paths` itself via `glob.glob(..., recursive=True)` - quoting is what makes `**` usable, since bash without `globstar` won't expand it. `~` is expanded too (bash leaves it alone inside quotes). A pattern matching directories still honours `-r`; a pattern like `*` that sweeps in non-PDFs drops them quietly, but a *named* file is taken at its word and left to fail loudly at `open()` if it isn't a PDF. Matches are deduplicated by resolved path (the same file can be reached by two patterns, or by both a pattern and a directory), and a pattern matching nothing warns while an input set yielding no PDFs at all is a `ValueError`. Files are reported relative to `get_display_base()` - the deepest directory common to every matched PDF - so a single directory or pattern still shows bare filenames, and only a genuinely spread-out input set shows longer paths. The word sample is the point of the tool for this codebase: a legacy indic font shows up as latin gibberish (`ubZ fnYyh`) alongside `no tounicode`, which is exactly the signal that it needs a `-fc/--font-conv` mapping
  - **Training-corpus mode** (`-tf/--training-font LABEL=REGEX` + `-nf/--not-required-font REGEX`, both repeatable, plus `-tc/--training-csv`, default `training_data/samples.csv`): the corpus builder for the font classifier in `machinelearning/`. Each `-tf` names a class of fonts-that-need-decoding, and each `-nf` names fonts that need none (all `-nf` regexps feed the single `not_required` negative class, so the families can be listed a few at a time). Both are matched against the font name the same way `-fc` matches its font names (anywhere in the name, case-insensitively, so one `nirmala\s*ui` catches `NirmalaUI`/`Nirmala UI`/`Nirmala UI,Bold`); first match wins and every `-tf` is tried before every `-nf`, so a font caught by both is treated as needing a decoder. **The corpus is the one csv `-tc` names, with a row per sample - `label,font,pdf,text`** (`TrainingWriter.CORPUS_FIELDS`), and it is the single source `machinelearning/features.py` trains from - nothing is written twice. Only `label` and `text` are learned from; `font` and `pdf` are carried because a class that looks polluted is a question the label alone cannot answer - a regexp like `chanakya='chanakya|TT[0-9A-F]+t[0-9]+'` matches a *shape*, not an encoding, so any unrelated `TT…t…` font lands in that class and only the font name says which. `pdf` is the document a sample was built in (a sample never spans two, since `flush()` runs between them). **Both tools name the corpus as a file, not a directory**: `-tc/--training-csv` writes it and `machinelearning.training -c/--corpus` reads it, each defaulting to `training_data/samples.csv` (`TrainingWriter.DEFAULT_CORPUS` / `training.DEFAULT_CORPUS`, kept in step so the pair of commands works with neither option given), and `features.read_corpus` opens exactly that path - a missing file or one without a `label`/`text` column is a fail-fast `ValueError`. The directory the options used to take was a leftover from the corpus being one `<label>.txt` file per class; that layout, and the fallback that read it, are gone. **One row is one sample and one sample is `-tw/--training-words` (default 50) words of text drawn in one font**: a single line of a PDF (~6 words) is far too little evidence to classify an encoding from, so `TrainingWriter.add_text` buffers the runs of a font in `self.pending` (keyed by font, not by class, so two fonts of one class drawn alternately don't interleave inside a sample) and only writes a line once it reaches that many words. `FontSurvey.survey_pdf` calls `TrainingWriter.flush()` after each document, so a sample never mixes two PDFs and whatever a document ends with is written out short rather than dropped (`-tw 1` restores one-sample-per-run). Worth the ~7x drop in sample count: on `test/test_pdfs` the same 5-class problem goes from CA 0.938 / macro-F1 0.904 at one run per sample to **CA 0.993 / macro-F1 0.969** at 50 words, with far fewer samples to train on. The per-class report prints the mean words per sample, which reveals a class made up mostly of end-of-document leftovers (a mean well under `-tw`). **Text drawn in a font matched by neither is dropped, never defaulted into `not_required`**: a font that in fact needs decoding but was swept into the negative class teaches the classifier the exact opposite of the truth, and the font name alone can't say which side an unnamed font belongs on - that being the very problem the model exists to solve. `TrainingWriter.get_label()` returns `None` for those and `get_dropped_report()` lists each dropped font with its sample count (top 25), which is the worklist for widening the regexps. Labels are class names read back out of the csv so they're restricted to `[A-Za-z0-9_-]`, `not_required` is rejected as a `-tf` label (pointing at `-nf`), duplicates and malformed `LABEL=REGEX`/bad regexps are fail-fast `ValueError`s, and `-tf` without `-nf` (no negative class), `-nf` without `-tf` (no positive class) and `-tc` without either are errors. One row is one sample and a sample can hold no newline (`' '.join(text.split())`), so a row is always a line and a run of pure punctuation is dropped as carrying no signal. The report gains a per-class section (sample count + which fonts fed it, flagging a regexp that matched nothing) plus the dropped-font list. **The unit of text is a `get_line_runs()` run - consecutive same-font spans of one line joined - not a span**: a single word is routinely split across spans, so a run is the smallest piece of text certain to be both whole and drawn entirely in one font. `survey_drawn_text` feeds records and the corpus from that same run, so the word statistics improve with it. The `-o` report (every font + a sample of its words) is what the regexps should be written from. **Type3 fonts are a `-tf` class (`-tf type3='^type3'`), not something to drop**: the Type3 fonts of a distilled gazette have a broken `ToUnicode` map repaired by `ToUnicodeFixer.fix_type3_fonts` (`indic2unicode/tools/fix_tounicode.py`, the same repair path `Main.repair_tounicode` drives), and their text extracts as devanagari with holes and stray latin in it (`रा% &पित क( अनुमित` in `test/test_pdfs/union_hindi5.pdf`) - as learnable a signature as latin gibberish. pymupdf names an unnamed Type3 font after its xref (`Type3 (314 0 R)`), which differs per file, so the regexp must be the bare `^type3`

- **machinelearning/**: Orange3 pipeline that learns which decoder a font needs from the *text extracted from it*, for the many PDFs whose font name identifies no encoding (`TT572t00`) and so can't be routed to a `-fc/--font-conv` converter by name. Training the model is standalone; the trained model *is* consumed by the parsing pipeline (`Main.detect_unknown_fonts`, see below). Trained on the classes `FontSurvey -tf/-tc` bootstraps from the fonts whose names *do* identify them. See `machinelearning/README.md`
  - `features.py`: corpus (the csv named on the command line, one sample per row, class in the `label` column) → sparse Orange `Table`. Every 1-to-5-word phrase is counted across the corpus and the `top_k` (default 10,000) most frequent become the feature set; a sample is the count of each of those phrases in it. Tokenization is whitespace-only on purpose - the corpus is deliberately *not* real language, so nothing can be assumed about what its punctuation means (in kruti-dev `{ks=` is one word). Ties in the frequency ranking break on the phrase itself, so the same corpus always yields the same feature set. `count_phrases` prunes singleton phrases once the table passes `prune_at` (2M) keys - a corpus of a few hundred thousand lines has millions of distinct 5-grams, nearly all seen once, and none of those can reach the top 10k anyway. Classes with fewer than `min_samples` rows are dropped with a warning (they can't be split across folds) rather than failing the run; samples left with no feature at all are counted and warned about
  - `training.py`: `python -m machinelearning.training -c training_data/samples.csv -m model/eng_hin_fonts.pkl` - stratified k-fold `CrossValidation` (`-k`, default 10) over the requested learners (`-le`, repeatable: `logistic`/`sgd`/`tree`/`forest`; default logistic+sgd), reporting CA, macro F1/precision/recall and a per-learner confusion matrix in samples; then trains `-fl/--final-learner` (default the first evaluated) on the whole corpus and pickles model+vocabulary+params together. Orange only ships a confusion matrix inside a Qt widget module (not importable headless), so `get_confusion()` counts it from `results.actual`/`results.predicted`. `-mc/--max-per-class` caps rows per class, since real corpora are wildly imbalanced (100k `not_required` lines vs a few hundred nirmala). SGD is constructed with `max_iter=1000` (Orange's default of 5 nowhere near converges on a matrix this wide)
  - `predict.py`: `FontClassifier(model_path).classify(text)` → `(label, probability)`, re-featurizing with the pickled vocabulary and params. Classify as much text of one font at once as is available (`-w` treats a whole file as one sample); a single short line carries little evidence. `Main.detect_unknown_fonts` is the pipeline's caller

- **NormalizeText.py** / **SentenceEndDetector.py**: Text normalization and legal sentence boundary detection

- **TextBox.py**: Textbox data model used throughout layout analysis
  - `get_char_lines()` / `extract_text_with_fonts()` / `extract_lines_with_fonts()` return the same text `extract_text_from_tb()` does, with a font mark at every font change (see the `-fn/--font-names` note under `HTMLBuilder.py`); `strip_font_marks()`, `mark_font_runs()` and `split_marked_text()` are the module-level helpers that work with them

- **Utils.py**: Shared helper functions

### Key Processing Pipeline

1. **PDF → XML Conversion**: Uses pdfminer (or ChromeLens/OCR for scanned copies) to extract structured text and coordinates
2. **Header/Footer Detection**: Cross-page analysis using sequence matching to identify repeating elements
3. **Multi-Column Detection**: Every page (all `pdf_type`s) is checked for a genuine 2-column layout and, if found, `all_tbs` is reordered into left-column-then-right-column reading order before any hierarchy detection runs (`Main.get_page_header_footer`)
4. **Content Classification**: Each page's textboxes are classified into semantic categories (including optional borderless-table detection)
5. **Type-Specific Processing**: `acts`, `sebi`/`sebi_circulars`, `egazette`, or default pipelines apply document-specific structuring
6. **HTML Generation**: Structured HTML with CSS styling based on content classification
7. **Manifest Generation**: For `egazette`/`sebi` documents with extractable images, an IIIF manifest is written alongside the HTML output, with a link to it added to the HTML itself

### Caching System

- **cache_xml/**: Stores intermediate XML files from PDF conversion
- **cache_pdf/**: Temporary storage for input PDFs (when needed)
- Cache files are automatically cleaned up unless `-x/--keep-xml` flag is used

### Command Line Options
- `-i, --input-filePath`: Input PDF file path (required)
- `-o, --output-directory`: Output directory for HTML file (required)
- `-fp, --start-page`: Start page number (optional)
- `-lp, --end-page`: End page number (optional)
- `-s, --sidenotes`: Flag if PDF has sidenotes
- `-a, --amendments`: Flag for PDFs containing amendments
- `-t, --type`: Document type — `acts | sebi | sebi_circulars | egazette` (affects processing pipeline)
- `-l, --loglevel`: Log level (error|warning|info|debug, default: info)
- `-g, --logfile`: Log file path (optional)
- `-x, --keep-xml`: Keep intermediate XML files in cache_xml folder
- `-lm, --line-margin` / `-cm, --char-margin` / `-wm, --word-margin`: pdfminer layout thresholds
- `-de, --doc-end`: Flag if PDF has a document-end symbol (`---`)
- `-fnc, --footnote-continuation`: Flag if footnotes continue across pages
- `-mip, --min-img-pixels`: Minimum pixel area threshold for image filtering
- `-ol, --ocr-language`: Tesseract language code for figure-text OCR (default: `eng`); one of `eng`, `asm`, `ben`, `guj`, `hin`, `kan`, `mal`, `mar`, `nep`, `ori`, `pan`, `san`, `snd`, `tam`, `tel`, `urd`
- `-ftx, --figure-text`: Enable OCR-based figure-text extraction (checked against a fasttext language-confidence threshold) and include it in the HTML output; images without confident text are dropped. Default: keep every figure as-is, no OCR/confidence check. Has no effect for `acts`/`sebi_circulars` (bluebell output never includes figure text) — those two types run figure-text extraction unconditionally regardless of this flag. `-oe`/`-ol` only take effect when this path actually runs
- `-oe, --ocr-engine`: OCR engine used for figure-text extraction (`-ftx`) — `tesseract` (default) or `paddleocr`. Only matters when figure-text extraction actually runs (see `-ftx` above); has no effect on page-text OCR (`-sc`/`ChromeLensParserTool`), which is a separate path. paddleocr only maps a subset of `-ol` language codes (`eng`, `hin`, `mar`, `nep`, `san`, `tam`, `tel` → `en`/`hi`/`mr`/`ne`/`sa`/`ta`/`te`); an unmapped `-ol` value with `-oe paddleocr` logs a warning and falls back to `eng` rather than failing
- `-sc, --scanned-copy`: Flag if the PDF is a scanned copy (routes through `ChromeLensParserTool`/OCR)
- `-te, --table-extract`: Enable borderless-table extraction (for borderless tables or scanned copies)
- `-pu, --public-base-url`: Public URL the output directory is served from, used as the base for IIIF manifest URIs (`egazette`/`sebi` only); falls back to the `PUBLIC_BASE_URL` env var, then `http://localhost:8000`
- `-sr, --server-root`: Local filesystem directory acting as the web server's document root (`egazette`/`sebi` only); the path from here to `--output-directory` becomes an extra URL segment between `-pu` and `manifest/<pdfname>/...` in the IIIF manifest. Never affects where files are written. Omit to have `--output-directory` itself act as the server root (no extra segment). `--output-directory` must be located inside it, or the tool fails with a clear error
- `-rt, --rights` / `-pi, --provider-id` + `-pn, --provider-name` / `-at, --attribution`: optional IIIF manifest metadata (`egazette`/`sebi` only) - license URI, presenting-organization id+name, and attribution text respectively. Only emitted when supplied; never defaulted or guessed
- `-fc, --font-conv`: `FONT=CONVERTER` mapping telling the tool that text in `FONT` is in a legacy indic encoding and must be converted with `CONVERTER` (one of `indic2unicode`'s: `aryan2`, `divya`, `surekh`, `chanakya`, `tunga`, `nudi`, `aklite`, `tamelango`, `vanavil`, `tommy`) - e.g. `-fc TT572t00=chanakya`. Repeatable, and several mappings can be comma-separated in one option. `FONT` is matched the same way the built-in font names are (anywhere in the pdf font name, case-insensitively) and takes precedence over them, so it can also redirect a font whose name *does* name a converter. Only needed for fonts whose name doesn't identify the encoding *and* that the font classifier (`-fm` below) can't place either; a malformed mapping or an unknown converter name is a fail-fast `ValueError`
- `-fm, --font-model`: the classifier that says what a font whose name identifies no encoding is drawing (default `model/eng_hin_fonts.pkl`; detection is skipped, with a debug log, when no model is there). `*.pkl` is tracked with Git LFS, so a fresh clone needs `git lfs pull` before the model is a real file rather than a pointer. See `Main.detect_unknown_fonts` below
- `-fl, --font-lang`: which of the models shipped in `model/` that classifier is, named by the language of the text this pdf's fonts draw - `hin` -> `eng_hin_fonts.pkl` (the default, so a run that names nothing behaves as it did before this option), `kan` -> `eng_kan_fonts.pkl` (`FONT_LANG_MODELS`/`get_font_model_path` in `Main.py`). A class is a way of encoding a *script*, so the devanagari model knows none of the kannada classes and vice versa, and asking either about the other's fonts is exactly the wrong-decoder-on-correct-text failure the detection path is tuned to avoid. A language the shipped set doesn't name is a fail-fast `ValueError` listing the ones it does; `-fm` names a model outright and so wins over `-fl` (a run giving both is warned about and takes the `-fm` model)
- `-nfd, --no-font-detect`: turn that detection off and go by font names and `-fc` mappings alone, as before the model existed
- `-fn, --font-names`: name the pdf font every run of text is drawn in, in the output itself - each contiguous piece of text drawn in one font is wrapped in `<span data-font="FONT">...</span>`, and a font the detector (`-fm`) was run on additionally carries `data-detected-font="CLASS"`, the model's own verdict about it whether or not that verdict was acted on. Html output only, so it is ignored (with a warning) for `acts`/`sebi_circulars`, which are written as bluebell

### Surveying fonts across a directory of PDFs
```bash
python -m source.FontSurvey -i <directory> [-r] [-mw 100] [-o report.txt] [-j fonts.json]
python -m source.FontSurvey -i "pdfs/**/sebi*.pdf"        # quoted: ** expanded by the tool
python -m source.FontSurvey -i pdfs/*.pdf archive/ one.pdf  # any mix of paths
```
Lists every unique font in the PDFs given by `-i` - which accepts any mix of directories, single PDFs and bash-style wildcard patterns (quote a pattern to have the tool expand it, which is the only way to use `**`) - ordered by how many documents actually draw text in it (ties broken by word count), with its type, format, embedded/not, encoding, whether it has a `ToUnicode` map, the files it is drawn in (ordered by the share of that file's words it accounts for, biggest first) and the page count it appears on, and up to `-mw` distinct words drawn in it (default 100). `-r` recurses into subdirectories, `-o` writes the text report to a file instead of stdout, `-j` additionally dumps the full survey (including the complete file list per font) as JSON. Useful for finding which fonts in a corpus need a `-fc/--font-conv` mapping - those show latin gibberish as their word sample and are marked `no tounicode`

### Building a font-classifier training corpus and model
```bash
# 1. corpus: one csv, one row per sample (label, font, pdf, text)
python -m source.FontSurvey -i pdfs/ -r -tc training_data/samples.csv \
    -tf nirmala='nirmala\s*ui' -tf krutidev='kruti\s*dev' -tf arialuni='arial\s*unicode' \
    -tf chanakya='chanakya|TT[0-9A-F]+t[0-9]+' -tf type3='^type3' \
    -nf 'times|arial|calibri|cambria|courier|helvetica'

# 2. cross-validate + train (Orange3)
python -m machinelearning.training -c training_data/samples.csv -m model/eng_hin_fonts.pkl -k 10 -mc 20000

# 3. classify text whose font name says nothing about its encoding
python -m machinelearning.predict -m model/eng_hin_fonts.pkl -t "fnYyh fodkl izkf/kdj.k"

# 4. the parser uses that model itself - no -fc mapping needed for those fonts
python -m source.Main -i union_hindi.pdf -o out/ -t egazette        # model/eng_hin_fonts.pkl
python -m source.Main -i union_hindi.pdf -o out/ -t egazette -fm /path/to/eng_hin_fonts.pkl
python -m source.Main -i kannada.pdf -o out/ -t egazette -fl kan     # model/eng_kan_fonts.pkl
python -m source.Main -i union_hindi.pdf -o out/ -t egazette -nfd   # names and -fc only
```
`-tf LABEL=REGEX` writes the text drawn in every font matching `REGEX` to the `-tc` csv labelled `LABEL`, `-nf REGEX` labels the text of the fonts needing no decoder `not_required`, and text in any font matched by neither is dropped (and reported); each row also carries the font and pdf it came from, which is what a polluted class is traced with. `machinelearning/` turns that csv into 1-5 word phrase features (top 10,000) and an Orange3 model. See `machinelearning/README.md`

## Development Notes

- The system uses coordinate-based analysis extensively - textbox positions determine content classification
- Header/footer detection uses similarity matching across pages (SequenceMatcher with 0.4 threshold)
- Multi-column detection (`Page.detect_multicolumn_layout`) runs for every page regardless of `pdf_type`, before header/footer-driven hierarchy detection; it's a pure reading-order fix (`all_tbs` reordering) with no new HTML/bluebell tags
- Amendment detection is a specialized feature for legal documents
- Overprinted-space removal (`Main.drop_overlapping_spaces`, run on the parsed XML right after `get_pages_from_xml()` and *before* `convert_indic_fonts()` and any layout analysis, so no downstream consumer of the XML ever sees these spaces): some PDFs paint a space that never advances the pen, the next glyph then being drawn back on top of it. Devanagari text does it routinely, where a conjunct is drawn as two glyphs and the bogus space lands between them, so pdfminer reports `िभन् न` for `िभन्न` and the word is split in two everywhere downstream (`Main.convert_indic_fonts` included, which would otherwise convert a broken-up conjunct - hence the ordering). Such a space is identified purely by coordinates: it sits *entirely inside* the x-range of the nearest real glyph beside it (`SPACE_OVERLAP_RATIO = 0.95` of its own width) rather than beside it, and the offending `<text>` element is removed from the tree. Full containment is what separates it from an ordinary space, not mere overlap - kerning legitimately pulls a letter back over the space before it (a `.` followed by a capital reaches ~0.6 of the space's width in `test/test_pdfs/odisha_act.pdf` / `sebi2.pdf`), while measured overprints are always exactly 1.0. Neighbours are the nearest *non-space, non-zero-width* glyph on each side, since a combining matra is emitted with a zero-width bbox sitting on its base consonant and says nothing about spacing. One guard: when the two glyphs on either side of the space overlap *each other* by more than `NEIGHBOUR_OVERLAP_RATIO = 0.1` of their own width, the text itself is drawn overlapping - a rotated diagonal watermark comes out of pdfminer with every char's bbox covering its neighbours' - and the space is left alone, since nothing can be concluded from an overlap there
- Legacy indic font conversion (`Main.convert_indic_fonts`, run on the parsed XML right after `get_pages_from_xml()` and before any layout analysis, so every downstream consumer sees unicode): a `<text>` element whose `font` attribute matches an `indic2unicode` converter key (`re.search('.*<key>.*')`, case-insensitive) is rewritten in place. Conversion is contextual (matras reorder, glyph pairs compose), so it runs over the longest run of consecutive same-font chars and the result is spread proportionally back over those char elements, keeping each one's bbox for the layout code. A converter key is also matched under the other names its font is known by in a pdf, via `INDIC_FONT_NAME_ALIASES` (module level in `Main.py`, keyed by converter key, values are name regexps merged into `get_indic_font_res`'s patterns): `krutidev` is aliased to `kruti[\s_-]*dev`, since a Kruti Dev pdf font is named with a space and a face number (`Kruti Dev 010`, as in `test/test_pdfs/gazette1.pdf`) and so never matches the unspaced converter key itself, and to `vivek` and `dev[\s_-]*lys`, **Kruti Dev's other two names**: a gazette masthead is routinely set in Vivek (`Vivek-BoldA`/`Vivek-NormalA` in `test/test_pdfs/act1.pdf`, `boilers_act.pdf`, `borderless_table.pdf`, `borderless_table2.pdf`; `Vivek,Bold` in `amendment.pdf`), and DevLys is named like Kruti Dev, for its face and face number (`DevLys 010`, `DevLys-020`) - in neither case does the name say anything about the encoding. `indic2unicode` maps its own `vivek`/`devlys` keys at the same converter object, so on a current build these aliases change nothing - they are what makes the equivalence hold on a build predating those keys, and what states in this repo that Vivek and DevLys *are* Kruti Dev. `krutidev`, `vivek`, `devlys` and `chanakya` are all one converter object inside `indic2unicode`, so all of this changes which fonts get converted, not how. No PDF in `test/test_pdfs` uses DevLys, so unlike the Vivek alias this one moved no baseline - it is untested against real DevLys output. **A font's name still often doesn't reveal its encoding** - `test/test_pdfs/union_hindi.pdf` uses `TT572t00`/`TT447t00`, chanakya-encoded and unmatchable by name (nothing else in the PDF identifies it either: no `ToUnicode`, latin glyph names in the `Encoding.Differences`, PUA glyph names in the embedded TrueType) - which is what `-fc/--font-conv`, and now the font classifier below, are for
  - **A glyph the pdf's `ToUnicode` map has no entry for is read as the character of its cid, for the converters that have tokens there** (`CID_PLACEHOLDER_RE`, `CID_FALLBACK_FONT_KEYS` and `Main.get_indic_char_text`, applied when a font run's text is assembled in `convert_indic_font_run`): pdfminer writes such a glyph as the literal string `(cid:315)`, the cid being the glyph's id in the font, while an extractor that keeps the glyph rather than dropping it (pymupdf) hands out `chr(315)` - and `indic2unicode`'s `fonts/kannada/tunga.py` carries a `LIG_` token at exactly that character, the cids of a Tunga pdf being the glyph ids of Tunga itself. Only a `<text>` element that is *entirely* the placeholder is one of these glyphs, so text of the document that merely reads like the pattern is left alone, as is a cid past the last codepoint. This is not an odd glyph here and there in a Tunga document: Tunga draws a consonant and the matra i or o of it as one glyph and these maps leave nine of those ligatures out, which is 209 glyphs in `test/test_pdfs/kannada-tunga.pdf` - one in the middle of every other word, each breaking the syllable the converter reads around it (`ಪ್ರಸ್ತಾವನೆಯ(cid:313)ಲ್` where the document says `ಪ್ರಸ್ತಾವನೆಯಲ್ಲಿ`). **`tunga` is the only key in `CID_FALLBACK_FONT_KEYS` and the set is not a list waiting to be widened**: `chr(cid)` is a reading of a glyph only where the font's cids are the codepoints a converter has tokens at, and in an ordinary subset font the cid is an arbitrary glyph id whose `chr()` is a control character carrying nothing. Handing one to a converter is *worse* than leaving the placeholder alone - the converter drops the character it cannot read, while the placeholder was at least visible in the output as the glyph that could not be recovered. Measured, not hypothetical: doing this for every converter turned `बाबा गंगनाथ माग(cid:18), मुकनराि` into `बाबा गंगनाथ माग, मुकनराि` in `test/test_judgment_pdfs/judgment59.pdf` (Nirmala UI, cids 3/18/24/27), quietly losing the reph. It is the same asymmetry the font detection is tuned around - a glyph left as it is loses an improvement, a glyph read wrongly destroys text - so a converter earns a place in the set by having tokens at these characters, not by being likely to
  - **Tunga (kannada) needs no `-fc` mapping**: `indic2unicode` registers `tunga`/`Tunga`/`Tunga-Bold` in `FontConv.converters`, so `get_indic_font_res`'s `.*tunga.*` already matches the subset names a Karnataka gazette carries (`BJFFHH+Tunga`, `BJFENJ+Tunga-Bold`). - Font detection from the text itself (`Main.detect_unknown_fonts`, run on the parsed XML between `drop_overlapping_spaces()` and `convert_indic_fonts()` - i.e. on the text as the PDF drew it, since converted text is exactly what the model was never trained on): every font that neither its name, nor a `-fc` mapping, nor a `ToUnicode` repair has placed is classified by the `machinelearning/` model, and a font the model places is registered as a regexp in `self.indic_font_res` exactly as a `-fc` mapping would be - so `convert_indic_fonts` (and the camelot path, which gates on the same list) picks it up without knowing where the answer came from. Detected entries go in front for the same reason `-fc`'s do: a verdict about *this* document beats a general rule about names. `-fc` still wins outright, because a font it names is never unplaced in the first place
  - **Model classes map to converters through `FONT_CLASS_CONVERTERS`** (module level in `Main.py`), which only needs an entry where the corpus label and the converter key are spelled differently (`nirmala` → `nirmalaui`); anything else falls back to the label itself and, failing that, is warned about and left alone (a model trained on a class this build of `indic2unicode` has no decoder for). `not_required` means the text is unicode already and is taken as it is. `type3` identifies the font correctly but has no converter to point at - `repair_tounicode()` has already put that text right before anything was extracted - so it too is taken as it is. `mangal` sits in `FONT_CLASSES_WITHOUT_CONVERTER` beside it for both halves of the same reason: `repair_tounicode()` places it too, and a Mangal that reaches detection at all is one the repair *could not* place, whose text is therefore still missing the characters of every glyph the shaper made (that map hands them `<0000>`, not the wrong character), and no decoder can put back what was never extracted. **`mangal_glyphs` is deliberately not registered in `fontconv.py` under the bare font name** the way `Arial Unicode MS`/`Nirmala UI` are: theirs name the *lossy* converters, which are for a PDF that was never repaired, while `mangal_glyphs` only reorders text the repair already put right. A Mangal whose map is sound extracts correct text, and name-matching it onto a reordering pass would turn `निर्माण` into `नर्मिाण` - so that converter is reachable through `get_repaired_font_res()` alone, which names only the fonts actually repaired in *this* document. An `arialuni`/`nirmala` verdict points at the lossy `arialuni`/`nirmalaui` converters rather than the reordering-only `*_glyphs` ones, because a font whose map *was* repaired is registered by `get_repaired_font_res()` and so never reaches detection
  - **Text is collected per font as runs joined with a space, not as one string of the font's chars**: the spaces between words are `<text>` elements of their own carrying no `font` attribute, so concatenating just one font's chars would run its words together and hand the model text tokenized quite differently from the corpus it learned on (which `FontSurvey` built out of whole `get_line_runs()` runs)
  - **A verdict is checked against the text it was reached on** (`get_detected_font_key`, `FONT_CLASSES_INDIC_TEXT` / `INDIC_SCRIPT_RE` / `FONT_DETECT_MAX_INDIC_RATIO`, all module level in `Main.py`): every class except the ones drawing indic text already (`arialuni`/`nirmala`, whose ToUnicode map is broken so they draw real devanagari that is merely the wrong devanagari; `type3`, put right by `repair_tounicode()`; and `not_required`) is a legacy 8-bit encoding overloading the *latin* codepoints, so its text cannot contain an indic character at all. When the model names one of those for text that is more than 5% indic by character, the answer is impossible whatever its probability, and the font is left alone with a warning. This is not hypothetical: the model calls `CIDFont+F1` of `test/test_pdfs/lsdebate.pdf` - a plain unicode CID font drawing 275,000 words of mixed english and hindi, littered with `(cid:214)` where its ToUnicode map has holes - `chanakya` **at probability 1.00**, and decoding it turned the whole debate into rubbish (`Eighteenth Series` as `म्पहीजममदजी ैमतपमे`). Nothing in the confidence said so, because the corpus has no class for text like that; the script of the text does. The check is deliberately asymmetric - a font wrongly left alone only loses the improvement detection was there to make, while a font wrongly decoded destroys text that was already correct - and a class the list does not name is assumed latin-source, so a decoder added later is guarded by default
  - **A font this tool corrects itself is never handed to the model** (`FONT_CLASSES_WITHOUT_CONVERTER`, `Main.get_type3_font_names()` and `FONT_DETECT_NO_CONVERTER_RE`, module level in `Main.py`): the two classes in that set are the ones `repair_tounicode()` puts right and no converter decodes, so the one verdict about such a font that is *true* is also the one that changes nothing, while every other verdict runs a decoder over text that is already correct - all risk and no gain. Skipping them at the *answer* stage (as `get_detected_font_key()` does) is therefore too late: the classes are skipped **before** classification, wherever the font can be recognised without asking. `mangal` is recognised by name, like `FONT_DETECT_SKIP_RE`'s latin faces. `type3` is not a name at all - a Type3 font carries no `BaseFont`, so pdfminer names it after its `FontDescriptor`'s `FontName` and calls it `unknown` when it has none - so it is read off the pdf itself with pymupdf, from the same repaired copy the rest of the run reads. `ToUnicodeFixer` gives every Type3 font it *does* repair a descriptor naming the font whose glyphs it read (`Arial Unicode MS`), which is what points it at `arialuni_glyphs` via `get_repaired_font_res()`, so those are placed long before detection; what this skip catches is the Type3 fonts the repair found **nothing to fix** - whose maps were already sound and whose text is therefore already correct. Five of the eight Type3 fonts of `test/test_pdfs/union_hindi5.pdf` are exactly those, and a retrained model called the clean devanagari they draw `arialuni` at a probability of **1.00**, running the lossy `ArialUni` decoder over correct text and dropping every character it has no token for (`आदेश` → `आदे`, `[फा. सं.` → `[ा. सं.`, `अजय कुमार भल्ला, गृह सिचव` → `अयि कुमार भल्ला, गृह सनर्च`, and the `________` rule line emptied outright). Nothing in `get_detected_font_key()`'s guards could catch it - `arialuni` is in `FONT_CLASSES_INDIC_TEXT` precisely because a broken Arial Unicode MS legitimately draws devanagari - which is why the guard has to be that the font never reaches the model
  - **The standard latin faces are whitelisted out of detection entirely** (`FONT_DETECT_SKIP_RE`, module level in `Main.py`): a font named `times|arial|calibri|cambria|courier|helvetica|verdana|tahoma|garamond|book antiqua|bookman|liberation|nimbus|myriadpro|minionpro|segoe|malgun|yu gothic` is never handed to the model at all. This is the name-based half of the same guard `get_detected_font_key()` applies to the model's *answers*: such a name already places the font as drawing plain latin unicode (these are the very families `FontSurvey -nf` builds the corpus's `not_required` class out of), so detection has nothing to add and a false positive on one of them would decode text that reads perfectly well as it is - the asymmetry the whole detection path is tuned around. Matched anywhere in the name, case-insensitively, exactly as `-fc` and the built-in font names are, so a subset prefix and a style suffix match too (`ABCDEF+TimesNewRomanPSMT`, `Times New Roman,Bold`); the multi-word names carry an optional separator (`book[\s_-]*antiqua`) because a pdf spells them both ways (`Book Antiqua` and `BookAntiqua`, `Yu Gothic` and `YuGothic`). The check sits in `get_unknown_font_texts` **after** the `get_indic_font_key()` lookup, so a font the ToUnicode repair has already placed never reaches the whitelist at all (`Arial Unicode MS` in `test/test_pdfs/union_hindi2.pdf`, `union_hindi4.pdf`, `gazette1.pdf`). **`arial` catches exactly one name that is not a plain latin face, and `FONT_DETECT_SKIP_EXCEPT_RE` (`arial[\s_-]*unicode`) carves it back out**: Arial Unicode MS is a devanagari font whose ToUnicode map was built wrong, so it genuinely needs a decoder, and whitelisting it by name would - on a build of `indic2unicode` without `ToUnicodeFixer`, where `repair_tounicode()` places nothing - have thrown away the model's `arialuni` verdict, the only thing left that could place it. The whitelist is therefore `SKIP_RE and not SKIP_EXCEPT_RE`; every other `arial*` name (`ArialMT`, `Arial-BoldMT`, `Arial,Italic`) still skips detection
  - **Two thresholds, both module-level constants**: `FONT_DETECT_MIN_WORDS` (20) is how much text a font must draw before it's classified at all, and `FONT_DETECT_MIN_PROB` (0.5) how sure the model must be before its answer is acted on. Both exist because confidence collapses on short samples - measured on `union_hindi.pdf`, 1000 words of `TT572t00` score 1.00, 100 words 0.97, 20 words 0.77, 5 words 0.81 *for the wrong class*, and a font drawing 2 words gets the model's prior. Below either threshold the font's text is left exactly as it is, which is the pre-detection behaviour; decoding on a coin toss would corrupt readable text. `FONT_DETECT_MAX_WORDS` (20,000) caps what's featurized per font, since evidence saturates in the low hundreds while the features are every 1-to-5-word phrase of the text
  - The model (`Orange`, ~1s to import) is loaded lazily on the first document that actually has an unplaced font, and a failed load is remembered so it's reported once rather than per font per document. A missing model, a failed load, and a failed classification all degrade to "leave the fonts as they are" with a log line, never to an exception - detection is an improvement on the name-matching path, not a dependency of it

- Broken-`ToUnicode` repair (`Main.repair_tounicode`, run in `Main.__init__` before anything reads the PDF, so pdfminer *and* camelot both see the repaired text): a gazette set in a real unicode font can still extract as gibberish, because its `ToUnicode` map was built by pairing the glyphs of a run with the characters of that run one by one and devanagari shaping moves matra_i and the reph, so the pairing slips (`निर्माण` extracts as `जिमावण`). The glyphs are drawn correctly, so `indic2unicode`'s `ToUnicodeFixer` (`tools/fix_tounicode.py`, imported behind a guard - without it the repair is skipped and everything else works) rebuilds the map out of the embedded font program itself: the subset's `cmap`, its surviving `uniXXXX` glyph names, and its `GSUB` rules, which say which glyphs the shaper made out of which others (a conjunct is spelled out of its parts, a half form is consonant+halant, a below-base form halant+consonant), with a per-font hand table for the glyphs a subset describes none of those ways. The repaired copy is written to `cache_pdf/tounicode/` and `self.pdf_path` is pointed at it. **`Arial Unicode MS`, `Nirmala UI` (including their `,Bold` styles, which `font_lookup_key` folds into the family) and `Mangal` all carry a broken map** - `test/test_pdfs/union_hindi2.pdf`/`union_hindi4.pdf`, `test/test_pdfs/gazette1.pdf` and `223221.pdf` respectively. **`Mangal` is broken a third way and is repaired by a different key**: its map hands every glyph the shaper made `<0000>` outright, so the half forms, conjuncts, matra_i and reph are not the *wrong* character in the extracted text but *no* character - a raw NUL, which is why such a PDF used to fail XML parsing outright (see `ParserTool.parse_xml` above). Its subset carries neither a `cmap` nor a `post` nor a `GSUB`, only outlines, so nothing in the font says what those glyphs are and they come from `MANGAL_OUTLINES`, a table keyed by **what a glyph draws** (a signature of its outline) rather than by its glyph id, because this producer renumbers the glyphs of every subset - a gid table read from one document would silently corrupt the next. The readings in it were established by lining the PDF's glyph stream up against an OCR of the same pages. The same renumbering is why `ToUnicodeFixer.glyph_strings` will only carry a glyph's string from one subset of a font to another when both subsets **number their glyphs alike** (`glyph_count`, i.e. the font program's `numGlyphs`): a subset that keeps the glyph order of the font it was cut from counts all of that font's glyphs however few it carries, so the two Nirmala UI styles in `gazette1.pdf` both count 4923 and may share, while 223221's Mangal is carried both as 886 glyphs (naming 339) and as 136 (naming none) and may not - without the check the first hands the second its own digits and punctuation and turns the document to rubbish. **Outlines cannot answer this**, which is why the check is not an outline comparison: the bold of a family draws every glyph differently from its regular yet numbers them alike, so holding a donation to a matching outline refuses exactly the sharing `font_lookup_key` folds the styles together for (it silently cost `gazette1.pdf` a `्र`). Outlines are still what `MANGAL_OUTLINES` is keyed by - identifying *one* glyph is a different question from deciding whether two subsets share a numbering. **A font with an outline table is only repaired when its map actually has holes** (`has_map_holes`): the holed map is the fault that table was read for, and a Mangal subset that does describe its own glyphs carries the *other* fault (the shaping slip) which this build repairs only partially - on `test/test_pdfs/sebicirculars4.pdf` that partial repair turned an accidentally-correct `बोर्ड` into `बोडड`, so such a font is left exactly as it is. Repaired text is *correct but still in the order the glyphs are drawn in*, so `get_repaired_font_res` points those fonts at the reordering-only converters (`arialuni_glyphs` / `nirmalaui_glyphs` / `mangal_glyphs` / `nudiuni_glyphs` / `tauelango_glyphs` / `ilasundaram_glyphs` / `marutham_glyphs`) rather than at the lossy `arialuni` / `nirmalaui` ones, which are for a PDF that was **not** repaired; the repaired regexps are prepended to `self.indic_font_res` so they win over the name-based ones. **A repaired font's regexp matches the whole font name** (`^(?:.{6}\+)?<name>$`, the optional part being the six letter subset prefix `ToUnicodeFixer.base_font` strips), unlike `get_indic_font_res`'s name-based ones which match anywhere: this one says *this* font in *this* document was really repaired, and a font whose name merely contains it was not. For these fonts the hand table is all there is, and a subset numbering its glyphs differently is left exactly as it is rather than repaired from a font that says nothing. **`fix_simple_font()`** repairs the embeddings that carry no map at all: a simple font is addressed by a byte rather than by a glyph id, so `byte_glyphs()` reads the byte→glyph id mapping out of the subset's own cmap - the one question this producer's cmap does answer - and a map keyed by the byte is *created* for the font with `set_tounicode()`, the way a type3 font's is; a byte the table says nothing about is still written out, with the character `WinAnsiEncoding`/`MacRomanEncoding` already gives it (`SIMPLE_ENCODINGS`), so an extractor that does not fall back to the encoding is not left with nothing for it, and a subset that keeps no cmap at all cannot be repaired and is logged and left alone. pdfminer prefers a `ToUnicode` to the encoding for a simple font, which is what makes that work at all. **A font that carries no map at all is now built one rather than skipped**, which is the third change and the only one that is not specific to this font: `fix_font` used to return at once when there was no `ToUnicode` to walk, so every glyph of such a font extracted as `(cid:N)` - 13 of the 14 `TAU-Marutham` subsets of `tamilnadu/2023-03-28/Extraordinary_104_Part-IV_Section-1.pdf` are carried that way. There is nothing there to be right or wrong, so the map is built out of what is known about the glyphs and written to the font, the code of a glyph being its glyph id once identity encoding has been checked
  - **TAU-Marutham's whole font is 423 glyphs and `TAU_MARUTHAM` (`tools/fix_tounicode.py`) reads them off the blocks it lays them out in**: **49..95 one glyph per assigned codepoint of the tamil block** in codepoint order and skipping `ஶ` - the same 47 codepoints `Uni-Ila.Sundaram` lays out, which is why the list and the consonants of it are now named `TAMIL_CODEPOINTS_NO_SHA`/`TAMIL_CONSONANTS_NO_SHA` and serve both - then **120..141 and 142..163** every consonant with the sign `ி` and with the sign `ீ`, **164..182 / 183..201** the sign `ு` and the sign `ூ`, and **212..230** every consonant with a pulli on it, with `ஸ்ரீ` a ligature of its own at 208. **The latin and the punctuation are in the table too** - 3..45 the macintosh standard glyph order as far as `@` and then the ascii punctuation that follows the capitals, 260..285 `A`..`Z` and 286..311 `a`..`z` - not because they need repairing (every map of the corpus that names one names it what the table does, bar the two double quotes, which one producer numbers as the codepoints following `‘` and `’` in the same way it writes `஋` for `எ`) but because a subset carrying no map at all has to be built a whole one, and a map naming only the tamil would leave that document's digits, spaces and punctuation extracting as the control characters of their glyph ids. Two things are peculiar to it. The `ு`/`ூ` blocks are **19** letters wide, not 18: unlike every other font here this one draws those two signs into `ஜ` as well as into the eighteen letters of tamil proper, and codepoint order puts `ஜ` in the middle of the eighteen (166 is `சு` and 169 `டு`, so the two glyphs between them are `ஜு` and `ஞு`). And **the one font lays its blocks out both ways**: the two signs drawn into a letter run through the consonants in codepoint order, as `Uni-Ila.Sundaram`'s do, while the pulli block runs through them in the order `langs/tamil.CONSONANT_TOKENS` gives, as TAU Elango's do - the maps of the corpus name 216 `ட்`, 220 `ப்` and 229 `ன்`, which is the script's order, and 128 `நி`, 129 `னி` and 130 `பி`, which is codepoint order, and the glyphs were rendered and read either way round to be sure of it. Every reading was rendered out of the embedded subsets and read against the pages that draw them, and the maps corroborate them: of the ~190 glyph ids any map of this corpus names, all but fifteen carry the reading these blocks give, and every one of the fifteen is the pairing slip TAU Elango's map has - a `ெ` handed the `வ` it was drawn in front of, a `ண` handed the `ை`. **Glyph 97 is the one composite in the font** and the one reading the maps and the page disagree on: it is the outline of 62 (`க`) shifted 277 units right, the wide form the gazette sets after a `ை` - `அறிவிக்கை` is drawn `அ றி வி க் ை 97` - and the producer's map calls it the tamil digit `௧`, which is drawn alike; it is read as the `க` the page shows, and the tamil digit block that reading would otherwise have anchored is left out with it. What the table leaves out is 46..48, 96, 98..110, 112, 118, 119, 202..211, 231 and everything from 234 to 259 - no subset of the corpus carries a glyph anywhere there and no map of it names one. 231 is the one that is missed: the pulli block is 24 wide where the eighteen letters and `ஸ்`/`ஷ்`/`ஜ்` account for 21 of it, so its grantha part runs in an order of the font's own with one slot in front of `ஷ்` that nothing draws. Like TAU Elango's the table is deliberately **not** held to a glyph count: 284 of the 380 font instances of the corpus carry a full 423 glyph subset and the rest truncated ones of 295, 288, 230, 229, 225, 222, 186, 39, 29, 25 and 24 glyphs, and that subsetter drops the glyphs off the end without renumbering what it keeps - the subsets are drawn at different scales, so they are compared by the proportions of their glyphs rather than by their coordinates, and every tamil glyph a short subset shares with a 423 glyph one has the same proportions there (only a few of the small punctuation marks measure differently), while their maps name what this table does. `TAU-Marutham-Bold` and `TAU---Marutham` are folded onto the same key by `font_lookup_key` and share the order (11 of 11 and 46 of 60 of the glyph ids their maps name carry this table's reading, the fourteen being the same slip again); `TAU-Marutham-SC700` is a key of its own and is named beside them because its map carries the same breakage, which is the opposite of `TAUElangoPanchali-SC700`, whose map is sound
  - **The repaired text needs the same reorder TAU Elango's does, and `fonts/tamil/marutham.py` is that pass whole** (`MaruthamGlyphs`, a `pass` subclass of `TauElangoGlyphs` as `fonts/tamil/ilasundaram.py` is, registered as `marutham_glyphs` through `fonts/glyphs/marutham_glyphs.py` and - like every `*_glyphs` converter - under no bare font name): once the map is right the two fonts are one script drawn one way. `ெ`, `ே` and `ை` go in front of their letter, `ொ` and `ோ` are drawn in two halves with the letter between them (`அச்சகத் தொழிலில்` is drawn `அ ச் ச க த் ெ த ா ழி ல ி ல்`), and a consonant with the pulli or with one of `ி`, `ீ`, `ு`, `ூ` on it is a single glyph - which is the whole of what `TauElangoGlyphs` reads. The one rule it inherits without being exercised on it is `ௌ`: this font draws it out of a `ெ` and the length mark `ௗ` as TAU Elango does, but no subset of the corpus carries a glyph for the mark, so `TAU_MARUTHAM` has no reading for it. Validated against a `tesseract -l tam` OCR of the pages themselves: on six pages of `tamil-marutham.pdf` **812 of the 861 distinct tamil words match the OCR word for word**, and not one of the 49 that differ is mis-read - they are words the OCR itself got wrong. The html the pipeline writes for that document carries 17,781 tamil characters, no `(cid:N)`, no word beginning with a vowel sign and no vowel sign written twice over, and the same holds at scale: the html of `tamilnadu/2023-04-26/Ordinary_17_Part-III_Section-1a-T-Sup.pdf`, the longest document of the corpus that draws it, carries 731,573 tamil characters, no `(cid:N)`, 15 words beginning with a vowel sign and 56 doubled signs (0.01% between them). Over the 163 documents of the corpus 80 glyphs of one of them still extract as `(cid:N)`, all of them the one embedding named `TAU-Marutham-Identity-H` whose font program cannot be read at all, so nothing says it is this font rather than another and it is left alone. **What camelot sees is a different matter**: it extracts with playa rather than with pdfminer, and playa reads a simple font through its `/Encoding` without looking at the `ToUnicode` the repair writes, so the latin of those embeddings reaches the bordered-table path undecoded (it passes through the converter untouched rather than being mis-read, the lexer having no token for it) - the same class of limitation the `tunga` note above records. Covered end to end by `tamil-marutham.pdf` in `test/test_cases.csv` (`tamilnadu/2021-08-25/Ordinary_34_Part-II_Section-2-T-Sup.pdf`, 10 pages, which draws `TAM_ELANGO_Panchali` and `VANAVILAvvaiyar` beside it and so exercises three tamil paths in one document) and by `testdata/marutham_glyphs`/`expected/marutham_glyphs` in `indic2unicode`'s own regression suite, 600 lines drawn from the corpus
  - **What a kannada baseline still gets wrong is the word boundaries, and that is pdfminer and not the converter**: a vattu is a zero-width glyph drawn *back* inside the letter in front of it, so pdfminer's word-gap test measures the next letter's gap from the vattu's position rather than from the end of the text and inserts a space in the middle of a word (`ಭೂಸ್ವಾಧೀನ` comes out `ಭೂಸ್ವಾ ಧೀನ`); a few producers also draw a real space between a letter and its own vattu, which `drop_overlapping_spaces` does not catch because it skips zero-width neighbours by design and the two letters on either side of that space do not overlap. Measured against the word boundaries the pdf itself draws, 30% of the kannada words of `kannada-nirmalaui.pdf` and 16% of `arial-unicode-kannada.pdf` reach the html split this way - the same artefact at roughly the same rate, present in the accepted baselines of every kannada case, and independent of which font drew the text. Raising `-wm/--word-margin` does not fix it: the manufactured gap is about half the next letter's width, so the threshold that would swallow it also joins genuinely separate words (`32‐14‐00ಎಕರೆ` at `-wm 0.3`)
- `-t egazette` is not the same as `-sc/--scanned-copy`: an eGazette PDF with a real text layer (e.g. a Tamil Nadu "change of names" notification) is parsed via pdfminer like any other document; only when pdfminer's XML extraction yields zero pages (i.e. the PDF genuinely has no text layer) does an `egazette` PDF fall back to `ChromeLensParserTool`/OCR (`Main.parsePDF`) - other `pdf_type`s in that situation are instead flagged `is_scanned_copy=True` and routed through `process_scanned_copy`
- Borderless table detection (`-te`) uses logistic-regression classifiers in `TableExtraction.py` trained online via reinforcement learning (reward = downstream table-quality outcome) - weights are per-run only, never persisted to disk
- Borderless tables that span page breaks are stitched across pages: a page whose trailing table is large (≥30% of the page), bottom-cut, or carries a `(1)(2)(3)…` column-ruler row hands a normalized column template to the next page via `Main.pending_continuation`, and `ContinuationClassifier` (coordinate-alignment features only) decides whether the top-of-page content is a continuation — which can drop the header row and carry only a subset of columns, or be a single-column overflow that passes the template through without emitting a table. A ruler isn't required generally - coverage/bottom-cut triggers work for any borderless table shape. Column positions adapt via `ColumnTracker`'s running average rather than a frozen snapshot, new columns can be promoted mid-chain from recurring unmatched content, and template propagation is a union (never a replace) so an established column can't be lost to one page's noisy detection - see the `TableExtraction.py` section above for the full mechanism. Threaded through `process_pages_acts` / `process_pages_sebi_circulars` (both reset `pending_continuation` at the start of the page loop so state never leaks across documents). Validated on `test/test_pdfs/borderless_table2.pdf` (a multi-page amendment schedule, ruler-seeded) and `test/test_pdfs/borderless_table.pdf` (a multi-page offences table with no ruler): both now stitch continuously across dozens of pages with near-zero content loss (verified by cross-checking every table-region candidate textbox actually lands in its table's dataframe) instead of stopping after a few pages or silently dropping rows to satisfy shape-mismatched acceptance thresholds
